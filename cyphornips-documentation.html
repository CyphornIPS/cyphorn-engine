CyphornIPS User Documentation

A practical guide to installing, configuring, and operating CyphornIPS — with worked examples for every major feature.

Official Release Documentation: This manual documents CyphornIPS v1.8.0. Every capability, configuration key, rule keyword, command, and file path described here reflects the current, verified implementation — not a roadmap.

1 Overview

CyphornIPS is an inline Intrusion Prevention System (IPS) for Linux. It sits between two sides of a trust boundary — a WAN side facing the outside world and a LAN side facing the network you're protecting, each of which may carry more than one interface — and looks at every packet that tries to cross from one side to the other. Traffic it trusts is forwarded; traffic that matches a rule or policy is logged, dropped, or reset, all in real time and without renumbering your network.

Two things make it fast enough to sit in the middle of live traffic: an in-kernel eBPF fast path that can drop already-blocked flows before they ever reach user-space, and a user-space engine that does the deeper work — reassembling TCP streams, decoding HTTP/TLS/DNS/QUIC, matching thousands of signatures at once, and extracting and hashing transferred files.

Traffic path — CyphornIPS as an inline bridge
                  +----------------------------------------------------------+
                  |                       CyphornIPS                          |
                  |         Transparent Inline Intrusion Prevention            |
 WAN interface    |                                                            |   LAN interface
(e.g. enp0s3)  ---+--> [eBPF/TC] --> [Decoders] --> [Rule + Policy Engine] ----+---> (e.g. enp0s8)
[Untrusted WAN]   |         |             |                    |               |   [Protected LAN]
                  |         v             v                    v               |
                  |   [Conn. track]  [Stream reasm.]     [File extraction]     |
                  |         |             |                    |               |
                  |         +-------------+--------------------+               |
                  |                       v                                    |
                  |            Verdict: PASS / DROP / ALERT / REJECT           |
                  +----------------------------------------------------------+

What it gives you, in short:

  • In-kernel blocking: once an IP is blocked, an eBPF classifier drops it in the kernel — before it costs any user-space CPU time.
  • Real protocol understanding: Ethernet, IPv4/IPv6, TCP/UDP/ICMP, DNS, HTTP/1.x, TLS 1.0–1.3, QUIC transport, FTP, and IKE are decoded, not just pattern-matched as raw bytes.
  • Snort/Suricata-style rules extended with dataset lookups and flowbits, so one rule can check membership in a 50,000-entry feed, or correlate two separate requests in an attack chain.
  • File extraction and hashing: files transferred over HTTP or FTP are reassembled, hashed (MD5/SHA-1/SHA-256/SHA3-384), classified by magic bytes, and optionally archived — with zero external dependencies.
  • Domain and country policy that block by category or by geography, with a built-in explain command that tells you exactly why a device was blocked.
  • Zero-downtime hot reload: rules, threat feeds, and policies update in place — no dropped packets, no restart.

2 What's New in 1.8.0

Everything below was found by running CyphornIPS on a live appliance carrying real household traffic. Treat this release as a developer preview: it has been verified on one machine, one architecture and one topology, and has had no independent security review.

Inspection threads — worker_count

What is a worker? One thread that takes a packet all the way: receives it, decodes its headers, matches it against the rules, decides, and then relays or blocks it. A single worker does that packet after packet, in sequence — and saturates exactly one CPU core.

On a four-core appliance that leaves three cores idle while the fourth chokes. When traffic rises above what that core can take, the capture ring fills and the kernel drops. A dropped frame still reaches its destination — the kernel forwards it — but CyphornIPS never looked at it. A blind spot, not an outage.

Measured on a four-core appliance under a 4096-flow flood:

WorkersShare of offered traffic inspectedCPU
165%55% / 0 / 0
3100%28.6% / 13.3% / 13.6%

The kernel does the splitting, not CyphornIPS. A small eBPF program reads the packet's addresses and ports and computes a worker index from them — and it normalises direction first, so a client's packet to a server and the server's reply land on the same worker.

That is not an optimisation but a correctness requirement: one TCP stream split across two workers leaves each reassembling from a gap, so both inspect an incomplete half and both report verdicts on it. That is worse than not inspecting, because it is inspection that reports with confidence.

Each worker therefore has its own flow table, and the memory budget is divided among them rather than multiplied: the total is the same whether one thread inspects or four.

Values and examples

/etc/cyphornips/cyphornips.conf
worker_count=0     # default: derive it from this machine
worker_count=1     # one thread -- for diagnosis, or to match pre-1.8.0 behaviour
worker_count=2     # keep two cores for something else on a four-core box
worker_count=8     # an eight-core server, one core reserved
ValueMeaning
0The default. Derived from this machine: one per core, less one for everything that is not inspection — the appliance tick, the control socket, the logs, the rest of the system. On a four-core box: 3 workers.
1One inspection thread. The behaviour before 1.8.0.
2..64Exactly this many. Refused out loud if the build cannot run it, logging what was asked for and what is running.

It changes no verdict. The same traffic produces the same alerts and the same blocks whatever the worker count — checked by a gate that replays the same captures split 2 and 4 ways and compares every verdict. It is also inert for offline replay (--pcap), which is forced to one worker, because several threads reading one file would make the result follow the scheduler.

How to check

bash
$ cyphornctl config | grep worker_count
worker_count                = 0  (in force: 3)

$ cyphornctl status | grep "Inspected Links"
  Inspected Links: wan(rx=49062 lost=0 0%) wlan0(rx=8 lost=0 0%) ...

Two columns on purpose: what you set, and what is running. If they differ, the reason is in the start-up log under [WORKER] — because a setting that is quietly ignored is indistinguishable from one that worked.

Speed

before   one long flow  13,514 us      a hundred short flows  787 us    14.5x

Three things that start, and are silently wrong

Do not set ProtectKernelTunables or ProcSubset=pid in the systemd unit. The engine writes /proc/sys/net/*/conf/<if>/forwarding — that is how it owns forwarding state — and with either set it can neither secure nor restore it. The tell: the appliance itself pings and nothing behind it routes.

NIC offload (GRO/LRO/TSO) must be off on every inspected link; disable_interface_offload = true is the default, so CyphornIPS handles it. With it on, the NIC hands over reassembled super-frames that never crossed the wire, and lengths and segment boundaries become fiction.

fail_mode = closed means stopping the service takes transit down on every inspected link — by design. Learn that before your first systemctl stop, not after.

cyphornctl diagnose checks all three and more, and prints the command that fixes each finding.

5 Installation & File Layout

CyphornIPS is distributed as a pre-built .deb. There is no compiler, no build tooling and nothing fetched from a network during installation: the package carries the engine, the eBPF programs, the GeoIP databases, the default rules and the systemd units.

Debian / Ubuntu package (arm64 or amd64)

This is also how you upgrade an existing install. Nothing under /etc/cyphornips/ is ever overwritten if it already exists.

bash — install or upgrade arm64
# arm64
curl -LO https://github.com/CyphornIPS/cyphorn-engine/releases/download/v1.8.0/cyphornips_1.8.0_arm64.deb

# Preferred: apt resolves any new library dependencies automatically
sudo apt install ./cyphornips_1.8.0_arm64.deb

# Equivalent with plain dpkg
sudo dpkg -i cyphornips_1.8.0_arm64.deb
sudo apt-get install -f -y   # only needed if dpkg reports missing dependencies

cyphorn-engine --version
cyphornctl --version

Match the package to your machine's architecture

A package is published per architecture, each under its own name. Install the one that matches your machine: an arm64 package will install on an amd64 machine and its binaries will not run, and the reverse is also true. Ask the machine:

bash
dpkg --print-architecture
# arm64  -> cyphornips_1.8.0_arm64.deb
# amd64  -> cyphornips_1.8.0_amd64.deb

Everything after installation — configuration, rules, cyphornctl — is identical either way. apt refuses a package that does not match the machine's architecture, so the mistake is caught at install time rather than after.

Upgrading an existing install

Same command, no extra steps: dpkg treats a newer .deb with the same package name as an upgrade, not a fresh install. Your live /etc/cyphornips/ — cyphornips.conf, domain_policy.conf, country-policy.conf, and everything under rules/ — is never part of the package payload, so it's left exactly as it was; only the binaries, the systemd unit, and the BPF object get replaced.

bash — upgrade in place
# Preferred: apt resolves any new library dependencies automatically
sudo apt install ./cyphornips_1.8.0_arm64.deb

# Equivalent with plain dpkg
sudo dpkg -i cyphornips_1.8.0_arm64.deb
sudo apt-get install -f -y   # only needed if dpkg reports missing dependencies

# Confirm the new version took effect
cyphorn-engine --version
cyphornctl --version

If the service was already enabled (systemctl is-enabled cyphornips says enabled), it stays enabled across the upgrade. The old binary is stopped just long enough to unpack the new one, and if it was running, the upgrade starts it again and says so — an inline IPS left stopped by its own upgrade is an outage nobody reported. A fresh install is the other case and deliberately does not start: its interfaces have not been configured yet.

Verify the package before you install it

A release publishes the package with a SHA256SUMS beside it. Installing a package whose digest you have not checked means trusting the download, and a network is not something to trust. The file for this release is cyphornips_1.8.0_arm64.deb:

bash — verify, then install
curl -LO https://github.com/CyphornIPS/cyphorn-engine/releases/download/v1.8.0/cyphornips_1.8.0_arm64.deb
curl -LO https://github.com/CyphornIPS/cyphorn-engine/releases/download/v1.8.0/SHA256SUMS

sha256sum -c SHA256SUMS
# cyphornips_1.8.0_arm64.deb: OK       <- install only if you see this

# or compare by eye against the published digest:
sha256sum cyphornips_1.8.0_arm64.deb
# b102ffc85a2d606759b312adc76cce06b843213406485a964d9c0f2bcde1ed7e  cyphornips_1.8.0_arm64.deb
Either OK, or do not install

A digest that does not match means the file is not the one that was published. Do not install it and do not retry hopefully — download again, and if it differs a second time the problem is not your network.

Upgrading from an older version, without the risk

dpkg treats a newer package of the same name as an upgrade, not a fresh install, and nothing under /etc/cyphornips/ is part of the package payload — so your configuration and your local rules survive untouched. The order below is what makes it reversible: the backup is taken before anything changes, and the verification comes after it is carrying traffic again.

bash — upgrade, step by step
# 1. Record what you are on, so you know what to go back to
cyphorn-engine --version
dpkg -l cyphornips | tail -1

# 2. Back up configuration and local rules -- this is the step people skip
sudo tar czf /root/cyphornips-config-$(date +%F).tar.gz /etc/cyphornips

# 3. Verify the new package (above). Do not skip to 4 without an OK.

# 4. Install. apt pulls any new library the release needs; dpkg does not.
sudo apt install ./cyphornips_1.8.0_arm64.deb

# 5. Restart, and give it a moment to attach and load rules
sudo systemctl restart cyphornips
sleep 10

# 6. Verify -- in this order
cyphorn-engine --version                 # 1.8.0
systemctl is-active cyphornips           # active
cyphornctl diagnose                      # should report nothing blocking
cyphornctl status                        # rules loaded, invariant holds
ping -c3 -I <an-inside-interface> 1.1.1.1   # traffic actually crosses
What to expect while it happens

With fail_mode = closed, transit stops during the restart — two or three seconds on a typical appliance, longer with a large rule set. That is by design: the window while the engine is down belongs to fail_mode. Upgrade at a time when that is acceptable.

Read the release notes before you restart. A capability that was inert in your old version may become live after the upgrade, and rules written while they matched nothing will start matching. Review country-policy.conf and domain_policy.conf before step 5, not after.

If something goes wrong, going back is the same install with the older package, plus the backup:

bash — roll back
sudo apt install --allow-downgrades ./cyphornips_<older-version>_arm64.deb
sudo tar xzf /root/cyphornips-config-<date>.tar.gz -C /
sudo systemctl restart cyphornips
cyphornctl diagnose

Uninstalling — completely and correctly

CyphornIPS owns the forwarding state of the links it inspects, which means the order of removal matters. Stop it and hand forwarding back explicitly first, then remove the package — removing it while it holds forwarding leaves an appliance that carries nothing and no longer has the thing that would fix it.

bash — remove, keep your configuration
# 1. Stop it and stop it coming back at boot
sudo systemctl disable --now cyphornips
sudo systemctl disable --now cyphornips-transit-guard.service 2>/dev/null
sudo systemctl disable --now cyphornips-transit-watch.timer 2>/dev/null
sudo systemctl disable --now cyphornips-feeds.timer 2>/dev/null

# 2. Hand routing back -- with fail_mode=closed, transit is down right now
sudo cyphorn-engine --restore-fail-mode --force

# 3. Confirm every inspected link forwards again BEFORE removing anything
for i in <wan-iface> <lan-iface>; do \
  echo "$i $(cat /proc/sys/net/ipv4/conf/$i/forwarding)"; done   # each must be 1

# 4. Remove the package, keep /etc/cyphornips
sudo apt remove cyphornips

That leaves your configuration, rules and logs in place — which is what you want if you will reinstall. To remove every trace:

bash — remove everything
# after steps 1-3 above
sudo apt purge cyphornips

# the package does not own these, so purge does not take them
sudo rm -rf /etc/cyphornips /var/log/cyphornips /var/lib/cyphornips
sudo rm -rf /usr/share/cyphornips /usr/lib/cyphornips
sudo systemctl daemon-reload

# 5. Confirm nothing is left running or listening
systemctl list-units 'cyphornips*' --all --no-legend    # no output
command -v cyphornctl cyphorn-engine                    # no output
ip link show type veth 2>/dev/null | head              # no leftovers
tc filter show dev <wan-iface> ingress 2>/dev/null      # no classifier left
Two steps not to skip

Steps 2 and 3. If you remove the package while the engine still holds forwarding closed, the appliance will carry no traffic afterwards and you will have deleted the tool that knows how to give it back. The manual repair is echo 1 > /proc/sys/net/ipv4/conf/<if>/forwarding for each link — better known before you need it than after.

6 Upgrading a Running Appliance

Installing over an existing CyphornIPS is supported and is the normal way to move between versions. This section is about doing it on a box that is carrying live traffic, where the failure modes are different from a fresh install.

Know this first: the upgrade stops the engine

Replacing the binary means stopping the process using it. The package does that for you and starts it again afterwards — but for those few seconds the engine is not running, and under fail_mode = closed that means every inspected link stops carrying traffic. On a home or branch gateway, everyone behind it notices.

Plan for a short interruption, or set fail_mode = open beforehand if uninspected traffic for a few seconds is the lesser evil for you. There is no third option: the engine cannot inspect while it is being replaced.

1. Take a backup you can actually restore from

Your configuration is never part of the package payload, so an upgrade does not overwrite it. That is the design — but a backup costs seconds and an assumption costs an evening.

bash
sudo tar czf /root/cyphornips-backup-$(date +%F).tar.gz \
    /etc/cyphornips/ /var/lib/cyphornips/version.json

# and write down what is running now, so you can compare afterwards
cyphornctl config  > /root/cyphornips-config-before.txt
cyphornctl status  > /root/cyphornips-status-before.txt
cyphorn-engine --version

2. Install the new package

bash
curl -LO https://github.com/CyphornIPS/cyphorn-engine/releases/download/v1.8.0/cyphornips_1.8.0_amd64.deb
sudo apt install ./cyphornips_1.8.0_amd64.deb

What happens, in order: the running engine is stopped, the binaries, the systemd unit and the BPF object are replaced, and the engine is started again if it was running before. A fresh install deliberately does not start — its interfaces have not been configured yet — but an upgrade puts back what it stopped.

3. Confirm it actually came back

Do not take the package manager's word for it. It reports on unpacking files, not on whether an IPS is inspecting traffic.

bash
cyphorn-engine --version          # the new version
cyphornctl --version              # must match the engine
systemctl is-active cyphornips    # active
cyphornctl status                 # health, enforcement posture, rule count
cyphornctl logs engine -n 30      # what it said on the way up
If cyphornctl --version disagrees with the engine

You have a second copy earlier in your PATH. The package keeps /usr/local/bin pointing at /usr/bin, but a binary someone copied there by hand overrides it and is not replaced by an upgrade.

bash
which cyphornctl        # expect /usr/bin/cyphornctl or a symlink to it
ls -l $(which cyphornctl)

4. Pick up the new configuration keys

An upgrade does not edit your cyphornips.conf

Config files are seeded from the packaged template only when they do not already exist. That is what keeps an upgrade from trampling your settings — and it also means keys added in the new version will not appear in your file. They fall back to their defaults, which is safe, but you will not see them and will not know they are there.

Compare your file against the template that shipped with the new version, and copy across anything you want to set explicitly:

bash
diff /etc/cyphornips/cyphornips.conf \
     /usr/share/cyphornips/defaults/cyphornips.conf

Then confirm what the engine understood — not what you think you wrote. A key it did not understand is silently ignored, and this is the command that shows the difference:

bash
cyphornctl config
diff /root/cyphornips-config-before.txt <(cyphornctl config)

5. Check what the new version turned on

A new version can add detection that was not running before. Reading the start-up lines once, right after an upgrade, is how you find out before your users do:

bash
cyphornctl logs engine -n 200 | grep -E 'INTEL|OVERRIDE|FORWARDING|FAST_PATTERN'

The [INTEL] lines name every intelligence feature, its action and how many values it loaded. If one of them says drop and you were not expecting it to block anything, change the word and reload — you do not have to restart.

Rolling back

Install the older package the same way. Your configuration is untouched by either direction, so a rollback is the same operation with a different file:

bash
sudo apt install --allow-downgrades ./cyphornips_1.8.0_amd64.deb

# or, on an arm64 appliance:
sudo apt install --allow-downgrades ./cyphornips_1.5.0_amd64.deb   # the release you are going back to
systemctl is-active cyphornips
cyphorn-engine --version

If you had already restored the backup from step 1 over /etc/cyphornips/, reload rather than restart so nothing stops carrying traffic:

bash
sudo cyphornctl reload all

Upgrading rules is not upgrading the engine

Two different things, and confusing them costs rules you meant to keep:

apt install ./cyphornips_*.debcyphornctl update rules
ReplacesBinaries, systemd unit, BPF objectrules/managed/, wholesale
Leaves aloneEverything under /etc/cyphornips/rules/local/, overrides.conf, ip-reputation.conf
Interrupts trafficYes, briefly — the engine is stopped and restartedNo — hot reload, no restart
Signature checkedBy your package managerEd25519 manifest signature, refused if invalid
Anything you changed inside rules/managed/ will come back

That directory belongs to cyphornctl update rules. Deleting a rule there lasts exactly until the next rule update, which reinstalls the whole file without asking. If you want a shipped rule disabled or its action changed, say so in overrides.conf — the one file no update touches.

7 Quick Start Walkthrough

This walks through the full loop once, end to end: configure the engine, start it as a service, write and load one custom rule, trigger it, and confirm the result — the same loop you'll use for every rule you write afterward.

  1. Point the engine at your two interfaces

    Edit /etc/cyphornips/cyphornips.conf:

    /etc/cyphornips/cyphornips.conf
    wan_interface = wan0
lan_interface = lan0

rules_dir           = /etc/cyphornips/rules
domain_policy_file  = /etc/cyphornips/domain_policy.conf
country_policy_file = /etc/cyphornips/country-policy.conf

log_level = INFO

  2. Start it as a systemd service

    bash
    sudo systemctl enable --now cyphornips
sudo systemctl status cyphornips

  3. Confirm it's alive

    bash
    cyphornctl ping
cyphornctl status

    ping should return PONG; status shows the PID, uptime, and how many rules loaded.

  4. Write one rule of your own

    Add a line to /etc/cyphornips/rules/local/local.rules — this is your file; upstream updates never touch it (see Managed vs. Local Rules):

    /etc/cyphornips/rules/local/local.rules
    alert http any any -> any any (msg:"Test rule: request to /secret-test-path"; http.uri; content:"/secret-test-path"; sid:1900001; rev:1;)

  5. Load it — with zero downtime

    bash
    cyphornctl reload rules

    Active connections keep flowing while the new rule set compiles and swaps in atomically.

  6. Trigger it and watch it fire

    bash
    # From a client behind the LAN interface
curl -s http://example.test/secret-test-path

# On the engine, in another terminal
cyphornctl logs alerts -f

    You should see a line for SID=1900001 with your msg text. If nothing appears, check cyphornctl status for the loaded rule count and confirm your traffic actually transits the WAN/LAN bridge.

  7. Ask the engine to explain a policy decision

    The same control socket also answers why a specific device was blocked from a specific domain — useful the moment a help-desk ticket says "the internet doesn't work":

    bash
    cyphornctl explain 192.168.1.25 facebook.com

    See Domain Policy & Interactive Explanation for a full sample of this output.

The transit guard — a safety net outside the engine

A script and two systemd units of their own, with their own sandbox profile and deliberately without ProtectKernelTunables or ProcSubset — so it can repair the exact fault that blinds the engine. Nothing inside a process can be relied on to repair a fault that blinds that process.

bash
cyphornips-transit-guard.service   Before=cyphornips.service
    opens transit and drops a state file recording it shut, so the
    engine records the truth rather than the last shutdown's damage

cyphornips-transit-watch.timer     every 30 seconds
    while the engine is RUNNING, reopens any inspected link that has
    stopped forwarding

It does not weaken fail_mode. While the engine is stopped it does nothing at all — that window belongs to fail_mode, and closed means closed. The rule it enforces is narrower and in tension with no setting: while the engine is running, the links it inspects must carry traffic. It is also inert in the relay model (accept_kernel_forwarding=false), where forwarding=0 is the correct setting.

Off switch: transit_guard=off in cyphornips.conf.

10 Logging

File I/O is completely decoupled from packet processing: three independent streams, each with its own thread and bounded queue, so disk latency or rotation never slows down the datapath.

StreamDefault pathQueueFocus
Operationalcyphornips.log4,096Lifecycle events, interface/offload status, rule compilation, hot reloads.
Rule matchrules.log8,192[RULE] match events and [RULE_LIFECYCLE] reload audits.
Security alertsalerts.log8,192[ALERT], [COUNTRY-POLICY], and [DOMAIN-POLICY] events.

A few things worth knowing

  • Never blocks the datapath: the level check happens before any formatting or allocation; if a queue fills up during an I/O stall, the newest event replaces the oldest and a counter (main_dropped, rule_dropped, alert_dropped) records it.
  • Repeated errors get collapsed: a flapping interface or repeated timeout is deduplicated into "repeated operational error suppressed (N times): <message>" instead of flooding the log.
  • Post-NAT client attribution: behind a NAT gateway, raw packets only show the gateway IP — CyphornIPS reads Netfilter conntrack to recover the real client and adds CLIENT=<ip> to alerts.
  • GeoIP/ASN enrichment: alert and rule-match lines carry SRC_COUNTRY, SRC_ASN, SRC_ORG and their DST_ equivalents.
  • ICMP correlation: an ICMP error is linked back to the transport session it relates to via CORR_PROTO, CORR_SRC, CORR_DST, CORR_REL.
  • Force rotation any time, without stopping traffic: kill -HUP <pid>.

11 Reading the logs

Direction

The logs report the packet's own source and destination, not the flow's. A rule matching a request writes the client as SRC; a rule matching the response writes the server there — and both land in the same file. That is why every line carries DIR=.

DIRMeaning
to_serverClient → server. SRC is the device that started the conversation.
to_clientServer → client. SRC is the remote server — which is why a site's address appears as the source in certificate alerts.
unknownThe flow's orientation was never established — a stateless UDP packet, for instance. It does not mean "to server".

Which device

Alerts carry CLIENT= naming the real device on your network, recovered from the connection-tracking cache — so an end user does not have to reason about NAT to read their own log. An absent field means the client could not be established, which is more honest than guessing it.

Coverage and health

The coverage equation balances: what the interfaces saw = what was inspected + what was dropped + the egress copy of a flow already inspected + what is in flight. That last term was added on 22 September 2026, and how it got there is how to read the invariant.

Why the invariant used to flash

The interface counts a packet the moment it lands in the capture ring. The engine counts it when it takes it out. Between those two instants the packet is real, lost by nobody, and in neither number. A burst filling the rings faster than the engine drains them made the equation disagree by the size of the backlog — measured on this unit at +2,307, recovering to -2 immediately. Nothing was lost and nothing went uninspected: the packets were in flight, and the equation had no term for in flight.

The term is measured, not derived: read by walking the ring's block descriptors and counting frames the kernel has handed over and the engine has not drained. Subtracting one counter from the other would have been easier and worthless — that difference is precisely what the equation checks, so a term built from it makes the check vacuous.

A worked example

This is a real line from this unit, four ports, during a 100 MB download:

cyphornctl status
Coverage: appliance_invariant=HOLDS(-24)
          nic=214880 prefilter_dropped=0 kernel_dropped=0
          capture_dropped=0 engine_received=147302
          skipped_egress=67602 in_flight=0
TermValueWhat it is
nic214880What the four interfaces saw. Reported by the devices themselves, derived from nothing else — which is what lets the equation fail.
engine_received147302What actually reached inspection.
skipped_egress67602The egress copy of a flow already inspected on ingress. A forwarding appliance sees every packet twice and the second copy is skipped on purpose, so no verdict is doubled. About a third of traffic here.
in_flight0In the capture rings: put there by the kernel, not yet taken out by the engine.
capture_dropped · kernel_dropped0 · 0Loss, as the kernel and the device report it. Zero here.
The arithmetic
147302 + 67602 + 0 + 0 + 0  =  214904
the interfaces saw          =  214880
                       out by  =     -24      within 256  -> HOLDS

The equation closes to within 24 packets. The bound is 256 because this appliance has four ports — 64 each.

A burst, or a shortfall?

With the term in place a small residual remains: the block each ring is still filling, whose packet count is not final until it retires. Measured on four ports under a sustained download at +5 to +66. Two keys in cyphornips.conf govern it:

KeyDefaultEffect
coverage_tolerance_per_port0 deriveHow far the equation may be out per inspected link. The residual belongs to a ring, so the bound does: four ports get four times the room of one, and a two-port appliance is held tighter than one flat number held it. The default is 64 per port.
coverage_violation_samples3How many consecutive breaches before VIOLATED is declared. 1 reports the first breach immediately.
The same delta, two different meanings
# a burst -- the engine was behind, then caught up
  +2307   ->    -2   ->    -2        not a violation, at any size

# a shortfall -- the packets keep not arriving
   +900   -> +1800   -> +2700        violation

# small, and it never heals -- this is the one a wider tolerance loses
   +300   ->  +305   ->  +310        violation

The second key is what no tolerance can do. A burst and a shortfall look identical in one sample — the interface ahead of the engine by thousands either way — and differ in the next: the burst heals, the shortfall grows, because the packets keep not arriving. Requiring a breach to repeat catches a persistent shortfall of seventy packets, which no tolerance wide enough to cover a burst ever would.

Nothing is hidden while it waits

The delta is printed either way, and a breach awaiting confirmation is logged at WARN naming the sample number and the bound. Only the verdict waits. The cost is that a genuine violation is announced a few samples late — seconds, in a signal that was previously flashing false often enough to be ignored.

The coverage line balances: what the interfaces saw = what was inspected + what was dropped + the egress copy of a flow already inspected + what is still in flight inside the capture rings. A forwarding appliance sees each packet twice, and the second copy is deliberately skipped so that no verdict is doubled.

And capture loss is a health state: DEGRADED at 0.1%, FAILED at 1%. Uninspected traffic is the one thing an IPS exists to prevent, so past that it is failed rather than degraded.

If a reload fails

An invalid rule file or malformed JSON dataset is rejected during validation — the error is logged to cyphornips.log, and the engine keeps running on its previous, still-valid configuration. Live traffic inspection is never interrupted by a bad reload.

cyphornips.conf itself does not hot-reload

The table above is the complete list of what cyphornctl reload can update live. Everything that lives in cyphornips.conf — the WAN/LAN interface names, GeoIP paths, log settings, the diagnostic port, and tls_log_ja3 — is only read once, at engine startup. There is no cyphornctl reload config. So if you flip tls_log_ja3 on to start capturing JA3 hashes for a baseline, or change any other line in cyphornips.conf, it has no effect until you run:

bash
sudo systemctl restart cyphornips

A restart is a brief service interruption (roughly 1–2 seconds), unlike the four reload targets above which never drop a packet.

Why GRO gets disabled automatically

Modern NICs often coalesce several incoming packets into a single oversized frame (Generic Receive Offload, up to 64 KB) to save kernel CPU. That's fine for a normal host, but fatal for a bridge: forwarding a 64 KB frame out an interface with a 1500-byte MTU makes the egress driver drop it outright, stalling the TCP flow. With disable_interface_offload = true (the default), CyphornIPS checks interface capabilities via ioctl(SIOCETHTOOL) at startup and turns GRO off on both WAN and LAN automatically.

15 How CyphornIPS Thinks

Before diving into configuration, it helps to have the mental model. Four ideas explain almost everything else in this document:

1. Every packet gets a verdict

Every rule and policy resolves to one of four actions: pass, drop/reject, or alert. When more than one applies, pass always wins, then drop/reject, then alert. See Action Precedence.

2. Sticky buffers scope your match

A rule doesn't grep the whole packet. You point at a decoded field first (http.uri, tls.sni, ja3.hash...) and every content that follows searches only inside that field.

3. Most specific rule wins

Domain policy and country policy both resolve conflicting rules the same way: an exact host beats a subnet, a subnet beats a wildcard. Priority only breaks ties within the same specificity. See Domain Policy.

4. Data updates, not code updates

Rules, threat feeds, and policy files are data the engine re-reads and hot-swaps atomically. Only a change to the engine binary itself needs a restart. See Running & Hot Reload.

17 Network Setup & Bridging

CyphornIPS bridges two network segments itself — frames arriving on WAN are inspected and forwarded out LAN, and vice versa.

Do not add a Linux software bridge

CyphornIPS bridges packets internally via AF_PACKET raw sockets and eBPF classifiers. Do NOT wrap the two interfaces in a kernel bridge (brctl addbr or ip link add type bridge) — they must stay independent devices.

Topology

18 Action Precedence

When several rules or policies match the same packet, CyphornIPS resolves the conflict the same way every time:

Conflict resolution
PASS (bypass)  >  DROP / REJECT (block)  >  ALERT (audit log)
PrecedenceActionEffect
1 (highest)PASSForwards immediately. Overrides every DROP, REJECT, and ALERT. No eBPF drop entry is written.
2DROP / REJECTDiscards the packet, installs the eBPF drop entry, logs to alerts.log.
3 (lowest)ALERTForwards, logs to alerts.log.

19 Performance & Kernel Acceleration

Gigabit-plus throughput with microsecond latency comes from two things working together: pushing already-known-bad traffic out to an in-kernel eBPF drop before it costs any user-space CPU time, and keeping everything that isn't packet forwarding — logging, conntrack lookups, reloads — off the single hot capture loop entirely.

In-kernel drop maps

MapKeyValueAction
cyphorn_policyIPv4 addressexpire_ns (uint64)Early drop (TC_ACT_SHOT) in the TC ingress hook, before the IP stack or user-space ever sees the packet.
cyphorn_policy_v6IPv6 address (16 bytes)expire_ns (uint64)Same, for IPv6.

Each entry carries its own expiry (from bpf_ktime_get_boot_ns()); once expired, the packet is allowed through and user-space garbage-collects the stale entry.

Logging never stalls the datapath

Worker threads enqueue events into bounded, non-blocking ring buffers (4,096 entries per stream); dedicated writer threads do the actual disk I/O. If a queue saturates during a disk stall, the worker just increments a drop counter and returns to forwarding — it never waits on I/O.

Why GRO/LRO get disabled

GRO/LRO coalesce packets into synthetic frames up to 64 KB, which distorts TCP sequence boundaries and can truncate what an application-layer parser expects to see. disable_interface_offload = true (the default) turns both off on WAN and LAN at startup via ethtool, preserving exact 1:1 packet fidelity across the bridge.

A single hot loop, and atomic reload

Packet capture, decoding, and rule matching run in one straight-line loop reading from the AF_PACKET raw socket — no locking between packets to coordinate, because there's nothing else on that loop to coordinate with. Everything that could otherwise stall it runs on its own background thread instead: the async log writers (see Logging), the Netfilter conntrack cache listener, and the diagnostic API server.

Rule, policy, and dataset updates use generation counters: a reload compiles the new version into a separate buffer, validates it, and only then swaps the active pointer and advances the generation — so the running engine is never left reading a half-updated rule set, and a reload that fails to validate simply never swaps in.

21 Configuration Reference

Settings resolve in strict order — a later source only wins where an earlier one is silent:

  1. CLI arguments (e.g. --wan, --lan, --config) — highest priority.
  2. Environment variables (e.g. CYPHORN_WAN_IFACE, CYPHORN_LAN_IFACE).
  3. Config file (/etc/cyphornips/cyphornips.conf, or a path given via -c).
  4. Built-in defaults.

The file format

Flat, dotted keys, one per line. key = value or key=value. # starts a comment, blank lines are ignored, values are trimmed, and booleans accept true/false, yes/no, 1/0.

There are no INI sections

A line like [detection] is not a heading. The parser has no concept of one, so it is ignored and everything you meant to put under it is read as though the heading were not there. Keys that look sectioned — geoip.enabled, udp.rate.window — are single flat keys that happen to contain dots.

Unknown keys are ignored silently. A typo is not an error; it is a setting that never takes effect. Check the start-up lines in the log rather than assuming a line was read.

22 Ports, limits & hardware

More than two interfaces

When a side carries more than one link, write them as a list. Separate the names with commas or spaces — either reads the same, and an interface name can contain neither, so there is nothing to get wrong.

cyphornips.conf
wan_interface = wan, lan1
lan_interface = wlan0 wlan1 wlan2

Every link in the list is inspected and enforced on, carrying the role of the side it was listed under. All five above are protected equally, not just the first of each.

Changed 22 September 2026

Until this date enforcement attached to the first two ports only; anything past them was inspected and alerted on and could not be blocked on. That was never a limit in the mechanism: the eBPF program does not read skb->ifindex at all, and the policy map is keyed on the flow tuple alone, so the same program on the same map enforces identically on any number of links. The limit was a struct that spelled out two ports. It is an array now.

The other spelling writes one port per line and names its role outright. It is the same mechanism, not a second one — but a list states the role once, so use this form when a link's role is not the role of the side it would be listed under: an asymmetric segment, or a trunk carrying both.

cyphornips.conf
port = eth2:inside
port = eth3:outside

Many ports, two roles. Inside and outside are the two sides of a trust boundary rather than two interfaces: source address validation compares where a packet arrived against where its address says it belongs, and that question has two answers however many wires there are. An unknown role is refused by name, because a port silently landing on the wrong side makes that validation answer backwards.

Sixteen ports at most, both sides counted. An interface may not appear twice: two capture sockets on one wire means every packet inspected twice and counted twice, and the coverage equation closes on a number that means nothing. A name longer than Linux allows is refused by name rather than truncated into one nobody wrote.

Forwarding and fail_mode cover the same links. That is not a detail: enforcement covering five links while forwarding owned two would be an appliance failing closed on two of them and open on the rest, while reporting itself fail-closed — half a guarantee. Both take the same list now.

The engine names every link and its status at start-up, and health asks enforcement how many links it actually armed rather than counting ports. A link inspected without being armed is reported DEGRADED.

[ENFORCEMENT] armed on wlan1 (inside, ingress+egress)

Nothing is conditioned on the hardware

CyphornIPS was written on a four-core router whose links are called wan and wlan1, and most of what it will be installed on is not that. No behaviour in the engine rests on a guess about what the hardware is: no interface name is searched for a substring, no role is derived from a port's position, no branch asks what kind of NIC this is. Roles come from the configuration, and sizes come from measuring the machine that is running.

Nothing optional refuses to start either: absent GeoIP databases, a conntrack socket that will not open, an empty rules directory — each degrades and says so rather than being treated as a reason to refuse to inspect.

Limits follow the machine

The rule ceiling, the capture ring and the memory defaults are all derived from the machine CyphornIPS runs on, not the machine it was built on. The engine says at boot what it measured and what followed:

cyphornips.log
[LIMITS] detected 3996MB RAM, 4 core(s) -> max_rules=30472 (16KB/rule),
         ring=2048KB/socket, memcap=999MB

max_rules=0 means derive, and is the default. Set a number if you have measured your own traffic. The derived ceiling is a memory decision; what you should actually load is a CPU question — see What rules cost.

Inspection threads

CyphornIPS has inspected on several threads since 1.8.0. The count is derived from the machine by default — one per core, less one — and set with worker_count. The kernel does the distributing, through an eBPF program that keeps both directions of a conversation on the same worker, which is a correctness requirement rather than a tuning choice. Measured on a four-core appliance under a 4096-flow flood: one worker inspected 65% of the traffic offered, three inspected 100%. Through 1.7.x inspection ran on one thread, so throughput followed single-core speed rather than core count. That is no longer true.

23 What the engine inspects vs. what the shipped rules cover

Two different questions

Does CyphornIPS understand this protocol? and do the shipped rules inspect it? are not the same question. Confusing them leaves you believing you are covered against something no rule looks for.

The engine parses eleven protocols and exposes their fields as rule keywords. The shipped rule set is Emerging Threats Open, written to run on several engines — so it leans on generic content matching rather than on one engine's own keywords. The consequence: some of what CyphornIPS parses well is not something the shipped rules exploit.

One rule, one line

CyphornIPS reads a rule file line by line and does not join lines ending in \. A rule split across lines the way Suricata documentation often shows it is refused with options are not closed by ')'.

And a rule that does not parse does not stop the reload — it is refused and the rest continue. If the count does not go up by as many rules as you added, one of them was not loaded; cyphornctl logs rules names it and says why.

What this means in practice

  • Web, DNS and TLS are densely covered by the shipped rules — which is where most attack traffic is.
  • Email and file transfer need rules you write. The engine gives you the fields; the shipped set does not use them.
  • Threat intelligence works independently of this. Domain, certificate, file-hash and JA3 blocking does not go through the ET rules, so it covers mail too when a message carries a link to a listed host.
  • cyphornctl status prints the rule count loaded on your appliance, which is the only count that matters to you.

24 Rule Language Basics

The rule language is Snort/Suricata-compatible, extended with sticky buffers, dataset lookups, and flowbits. Every rule is a header (action, protocol, addresses, direction) followed by parenthesized options:

Rule anatomy
action proto src_ip src_port direction dst_ip dst_port ( option1:val; option2; ... sid:XXXX; rev:1; )
No $HOME_NET / $LAN_NET style variables

Unlike Suricata, CyphornIPS has no rule-variable system. The src_ip/dst_ip fields only accept any, a literal address (192.168.1.50), or a CIDR (192.168.1.0/24) — with an optional ! to exclude it. Every address in the examples below is written out literally for this reason; swap in your own subnet wherever you see 192.168.1.0/24.

27 Payload Matching, Datasets & Flowbits

Beyond simple content matching, two keywords let a single rule scale to real-world threat intel and multi-stage attack detection.

Datasets — one rule, a whole threat feed (dataset:)

dataset: tests whether the current sticky buffer's value is a member of an external list — addresses, domains, hashes or strings — instead of writing, and paying for, one rule per indicator. Values are held in a single contiguous pool with a sorted index over it, so a list costs roughly its own size rather than a fixed slot per entry, and a lookup is a binary search: O(log N). The dataset binds to whichever sticky buffer was active when the keyword appeared.

Sticky bufferWhat the list holds
tls.sni, http.host, dns.queryHostnames.

file.name, http.uri, http.user_agentAny other sticky buffer works too — the list simply holds whatever that buffer contains.

Limits: 200,000 values per list, 16 MB per list, 32 lists loaded at once. A file exceeding a limit is truncated and a warning is logged. 28 Regular expressions (pcre)

CyphornIPS supports pcre through PCRE2 with JIT. The expression is a step in the payload chain rather than a check beside it, so R means "at or after where the previous content matched", and a within after a pcre counts from where the regex ended.

The backtracking budget

Every match runs under an explicit limit of 3,500 steps, counted in match steps rather than in time — so the same rule on the same packet gives up at the same point on a router and on a server. Most published pcre rules match on the raw payload, which is the expensive path — see What rules cost. The engine can read them; loading them is a measured decision, not a default.

29 What rules cost

The cost is not how many rules you load. It is what they match on.

8,698 application-layer rules (http. / tls. / dns. / ja3 / file.)34.6%0.03%

Measured on this appliance at 550 packets per second, replaying its own traffic. Four times the CPU from a seventh of the rules.

A step, not a slope

Adding a hundred raw-payload rules to the application-layer set takes loss from 0.03% to 17.73%, and the next five hundred barely move it. The first of them switches on reassembled-stream inspection for every TCP flow; after that the count hardly matters.

The trade is not 1,202 detections against nothing. At 36% loss every rule in the set misses a third of the packets, raw and application-layer alike. Fewer rules inspecting all of the traffic catch more than more rules inspecting two thirds of it.

Measure before you add

QUIC transport

QUIC wraps the TLS 1.3 handshake inside encrypted UDP Initial packets — so unlike classic HTTPS-over-TCP, there's no cleartext handshake to simply read. CyphornIPS instead:

  • Supports the QUIC v1, v2, and draft-29 salt derivations.
  • Derives the Initial packet keys via HKDF and decrypts the CRYPTO frame (AES-128-GCM).
  • Parses the recovered TLS 1.3 ClientHello and extracts the SNI, same as it would for TLS-over-TCP.
  • When domain policy calls for a block, installs a client-scoped eBPF UDP drop entry — instant, and without affecting other devices sharing the same NAT.

Only the Initial packet's handshake metadata is reachable this way — subsequent 1-RTT application data is encrypted with session keys CyphornIPS has no way to derive. See Limitations.

33 Certificate hygiene

CyphornIPS reads the X.509 certificate as it arrives and decides what is wrong with it. Every finding below is a property of the certificate or of the handshake it arrived in — none names a host or an authority, so the same rules work on any network.

Read this before you rely on it

In TLS 1.3 the certificate is encrypted and no passive inspector can read it — not CyphornIPS, not any other. Measured on this appliance's own traffic: 9 handshakes of 192 presented a readable certificate, or 4.7%. The inspection stays useful because malware and IoT devices often still use TLS 1.2 with bad certificates, but do not expect complete coverage.

The findings

KeywordWhat it means
tls.cert_expiredThe validity window has passed.
tls.cert_not_yet_validThe window has not opened — a clock skew, or a certificate minted for later. Distinct from expired because the remedy is the opposite.
tls.cert_self_signedIssuer equals subject: it vouches for itself, so the chain proves nothing.
tls.cert_name_mismatchThe name the client asked for is matched by neither the common name nor any subjectAltName. The strongest single signal here: an otherwise perfect certificate belonging to another name is what interception looks like from the wire.
tls.cert_no_namesNo common name and no subjectAltName: nothing to match a name against.
tls.cert_chain_incompleteOne certificate that does not sign itself, so the issuer was never sent. Reported rather than condemned: a client with the intermediate cached still succeeds.
tls.cert_long_validityA validity window longer than any public authority issues (825 days). Routine inside an organisation, worth seeing on a link to the internet.
tls.cert_impossible_windownotBefore is not before notAfter: malformed rather than expired.

Name matching

Name matching follows RFC 6125, and every way of getting it wrong is a certificate answering for names it was never issued for: a wildcard covers exactly one label, the leftmost one, so *.example.com covers a.example.com and covers neither a.b.example.com nor the bare example.com. When any DNS subjectAltName is present the common name is ignored entirely — which is what stops a certificate being accepted for a name it does not carry.

What it does not do

Chain-of-trust verification is absent: there is no CA store, so an untrusted root is not detected. Every finding above is read from the certificate itself and needs no external authority.

alert tls any any -> any any (msg:"CERT wrong name"; tls.cert_name_mismatch; sid:9200004; rev:1;)

34 File Extraction, Hashing & Threat Intelligence

CyphornIPS reassembles, hashes, classifies, and can archive files as they cross the bridge, and separately checks completed files against a fast exact-hash threat feed.

What actually extracts files

  • HTTP requests (to_server): client uploads (POST/PUT), including chunked transfer-encoding. Filenames come from Content-Disposition or the URI path.
  • HTTP responses (to_client): server downloads, same filename inference.
  • FTP data transfers: tracks the control channel (PORT, PASV, EPRT, EPSV) and extracts STOR/RETR payloads. The active command is exposed as ftpdata_command.
  • Not yet implemented: SMB and NFS are recognized by the rule parser but have no extraction adapter — rules targeting them parse fine but never fire at runtime.

Checksum blacklists (filemd5, filesha1, filesha256)

  • Syntax: filemd5:<filename>; etc. — the file is resolved relative to rules_dir (path traversal with .. is rejected).
  • List format: one hex hash per line; blank lines and #/; comments are ignored; whitespace and CRLF are stripped; hex is lowercased.
  • Strict validation: every line must be exactly the right length (32/40/64 hex chars) or the rule fails to load. A missing list file safely disables the rule without crashing the engine.
  • Lookup: the list is sorted with qsort() and queried with bsearch() — O(log N).
  • Inline hash strings (e.g. filemd5:"d41d8cd9...") are not supported — you always reference a list file.

Searching raw bytes (file.data)

alert http any any -> any any (msg:"Embedded Malicious Script in Upload"; file.data; content:"<script>eval("; nocase; sid:3403; rev:1;)

35 Domain Policy & "Why Was I Blocked?"

The Domain Policy engine classifies and enforces access to internet domains — over both DNS queries and TLS/QUIC SNI — without recompiling signature rules.

Two directives, plus an on/off switch

Syntax
# 1. Map a domain (and optionally custom patterns) to a category
domain <domain_name> <category> [custom_pattern1 custom_pattern2 ...]

# 2. Assign an action to a category, scoped to a client network, with a priority
policy <category> [scope] <BLOCK|ALLOW|DROP|PASS> [priority]

# Optional, top of file: enable/disable the whole policy file
state   active     # or: state disabled
enabled true       # or: enabled false
BLOCK/DROP/DENY/REJECT and ALLOW/PASS are the same two outcomes

There is no third or fourth action under the hood — DROP, DENY, and REJECT are accepted spellings of BLOCK, and PASS is an accepted spelling of ALLOW. Pick whichever reads clearest in your policy file; they behave identically.

Most specific rule wins

When several policy lines could apply to the same device, specificity decides — not the order you wrote them in:

A wildcard ANY rule with priority 1000 still loses to an exact-host rule with priority 0. Priority never lets a lower tier outrank a higher one.

37 Updates, Signing & Rule Ownership

cyphornctl update handles signature and threat-feed updates end to end: cryptographic verification, staged validation, atomic installation, and rollback if anything goes wrong.

Why updates are signed

CyphornIPS runs with elevated privileges to filter live traffic, so an unsigned or tampered rule feed would be a serious attack vector. The update client enforces:

  • Ed25519 manifest signatures — manifest.json is signed upstream and verified against the pinned key at /etc/cyphornips/update-signing.pub.
  • Mandatory verification by default — an unsigned or invalid manifest is rejected with zero changes to disk.
  • SHA-256 artifact hashes — every downloaded file is checked against the digest declared in the manifest before it's staged.
  • Staged, sandboxed validation — downloaded rules land in /var/lib/cyphornips/updates/staging/ and are test-compiled before going live.
  • Automatic backup & rollback — the previous rules/datasets are copied to updates/backup/ first, and restored automatically if compilation or hot-reload fails.

Managed vs. local rules

So an upstream update can never silently overwrite something you wrote, rules live in two directories:

  • /etc/cyphornips/rules/managed/ — upstream signatures, replaced by cyphornctl update rules.
  • /etc/cyphornips/rules/local/ — your own signatures. Updates never touch this directory.

Migrating from a flat rules directory

If you're upgrading from an older layout where every rule lived in one flat directory, cyphornctl update migrate sorts them out for you. It computes a canonical fingerprint for each rule (normalizing whitespace, comments, and formatting): signatures that match the official upstream manifest go to managed/rules.rules, and anything custom or modified goes to local/local.rules — with a backup taken first.

bash
sudo cyphornctl update migrate

40 Frequently Asked Questions

How is this different from a stateful firewall / iptables?

A firewall filters on Layer 3/4 headers (source/dest IP, port, protocol). CyphornIPS reassembles TCP streams, decodes application protocols (HTTP, TLS, QUIC, FTP, DNS), evaluates payload signatures by selecting candidate rules with a single Aho-Corasick automaton over every rule's fast pattern before any rule is evaluated, proven equivalent to a reference linear evaluator over the full corpus, extracts and hashes transferred files, and evaluates domain/country policy — all in real time.

How do I update rules without dropping traffic?

cyphornctl reload rules / reload intelligence / reload all. The candidate data is validated in an isolated staging area first; once verified, the engine swaps its active generation pointer atomically. Zero dropped packets, zero restart.

What's the difference between rules/managed/ and rules/local/?

managed/ is upstream content, replaced whenever cyphornctl update rules runs. local/ is yours — the update subsystem never writes to it.

How does cyphornctl explain decide the answer?

It evaluates domain policy against the live specificity tiers — exact host beats subnet beats ANY — and prints exactly which line decided, and why the others didn't.

Why do alerts show CLIENT=<ip> behind a NAT gateway?

Raw packets downstream of NAT only carry the gateway's IP. CyphornIPS queries Netfilter conntrack to recover the real client and appends it for forensic attribution.

Why is GRO disabled by default?

It coalesces packets into synthetic 64 KB frames in the NIC driver, which distorts sequence boundaries and breaks 1:1 forwarding across the bridge. disable_interface_offload = true prevents that.

How do I confirm the eBPF datapath is actually active?

tc filter show dev <wan-iface> ingress should show the classifier attached, and bpftool map show should list cyphorn_policy and cyphorn_policy_v6.

What happens on an invalid update signature?

The manifest is rejected outright — nothing is downloaded or staged, an error is logged, and the engine keeps running on its existing verified rule set.

43 Limitations & Disclaimer

No TLS decryption (MITM)

CyphornIPS never decrypts TLS

It does not terminate sessions, forge CA certificates, or decrypt application data. It works entirely from what's unencrypted in the handshake: SNI, JA3 client fingerprints, X.509 certificate fields, and negotiated TLS version.

QUIC scope

Only the Initial packet's CRYPTO frame (the TLS 1.3 ClientHello) can be recovered. Subsequent 1-RTT application data uses session keys from a Diffie-Hellman exchange that CyphornIPS cannot derive.

Asymmetric routing

CyphornIPS is stateful: TCP reassembly, flowbits, and protocol tracking all require both directions of a flow to cross the same bridge instance. If upstream routing sends return traffic a different way, stream reassembly won't complete.

Topology

CyphornIPS is a dual-interface inline appliance. Scaling across multiple physical chassis requires an upstream Layer 3 load balancer — there's no built-in clustering.

Latency under concurrency is unmeasured

The threading is measured by what it inspects: one worker inspected 65% of a 4096-flow flood, three inspected 100%. What is not published is the latency the engine adds to a packet with several threads running. The existing benchmark measures by replaying captures offline, and offline replay is forced to a single worker so its output stays reproducible — so it cannot answer the concurrency question however often you run it. Measuring it needs a new instrument, and that does not exist yet. If a latency ceiling matters to you, measure it on your own load before putting the appliance in the path.
