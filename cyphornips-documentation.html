CyphornIPS User Documentation

Official user reference and administration guide for configuring, deploying, and operating CyphornIPS.

Important Notice: CyphornIPS 0.1.0 is an experimental release. This documentation describes only functionality verified in the released package.

01 Overview

CyphornIPS is an inline network Intrusion Prevention System (IPS) and monitoring tool for Linux. It operates as a transparent network bridge between two dedicated interfaces—a WAN interface (external network) and a LAN interface (internal network).

CyphornIPS inspects transit packets passing between both interfaces, evaluates traffic against configured signature rules and domain intelligence policies, and applies enforcement actions (allowing, logging alerts, or dropping malicious traffic inline).

05 Quick Start

Follow these steps to deploy and run CyphornIPS on your host:

  1. Identify Network Interfaces:
    bash
    ip -br link
    Identify the actual network adapter names on your machine (e.g., WAN: enp0s3, LAN: enp0s8).
  2. Configure Interfaces & Rules: Edit /etc/cyphornips/cyphornips.conf with your interface names:
    /etc/cyphornips/cyphornips.conf
    wan_interface = enp0s3
lan_interface = enp0s8
rules_dir = /etc/cyphornips/rules
  3. Add Custom Signature Rules: Place your signature rules in /etc/cyphornips/rules/ (e.g. /etc/cyphornips/rules/custom.rules):
    /etc/cyphornips/rules/custom.rules
    drop icmp any any -> any any (msg:"Drop all ICMP traffic"; sid:1000001; rev:1;)
  4. Launch Interactive Dashboard:
    bash — Launch Dashboard
    cd /usr/lib/cyphornips && sudo /usr/bin/cyphorn-engine
    Or specify interfaces directly via CLI:
    bash — Launch with CLI Interfaces
    cd /usr/lib/cyphornips && sudo /usr/bin/cyphorn-engine -w enp0s3 -l enp0s8

06 Network Setup

CyphornIPS operates inline between two distinct network segments:

  • WAN Interface: Connected to the upstream gateway, firewall, or external internet link.
  • LAN Interface: Connected to the internal switch, protected local network, or downstream host.
Interface Requirements

The WAN and LAN interface names must be two distinct network interfaces on the host. CyphornIPS validates interface parameters upon launch and will exit with an error if the same interface is provided for both roles.

Mode 3: Administrative Control & Zero-Downtime Hot Reload (cyphornctl)

CyphornIPS includes a dedicated administrative CLI utility cyphornctl that communicates directly with the running engine process over a secure local Unix domain socket (/run/cyphornips/control.sock with /tmp/cyphornips_control.sock fallback). This enables live status queries and zero-downtime hot reload of detection rules and threat intelligence datasets without interrupting packet inspection.

Atomic Build-Then-Swap Architecture

When a reload is requested, CyphornIPS reads the target files from disk and compiles a new in-memory store in isolated staging memory. Only when all rules or dataset records are successfully validated does the running engine atomically swap the active pointers during its main loop. Traffic continues flowing with zero packet drops. If a rule contains a syntax error or a JSON dataset is corrupted, the reload is rejected, an error is reported, and the existing active configuration remains in effect.

CommandTarget SubsystemOperational Effect
cyphornctl statusAll SubsystemsDisplays live runtime status, frame/byte counters, active rule count, dataset record count, and reload timestamps.
cyphornctl status jsonAll SubsystemsOutputs machine-readable JSON telemetry for monitoring agents and automation scripts.
cyphornctl pingControl IPCVerifies control socket connectivity and health of the running engine (returns PONG).
cyphornctl reload rulesDetection RulesRe-parses all .rules files in rules_dir and atomically updates active inspection tables and eBPF maps.
cyphornctl reload intelligenceFile IntelligenceRe-reads and validates the JSON threat dataset and atomically replaces the hash lookup index.
cyphornctl reload allRules & IntelligenceAtomically validates and swaps both the rule store and File Intelligence dataset simultaneously.
bash — cyphornctl Administrative Examples
# Query engine operational and reload telemetry
cyphornctl status

# Reload detection rules after updating files.rules
cyphornctl reload rules

# Reload File Intelligence after updating cyphorn-file-intelligence.json
cyphornctl reload intelligence

# Reload all rules and intelligence feeds simultaneously
cyphornctl reload all

# Test control socket connectivity
cyphornctl ping

Signal-Based Hot Reload

In addition to cyphornctl, the running engine process listens for standard POSIX signals:

  • SIGHUP — Triggers combined atomic reload of all rules and File Intelligence datasets (equivalent to cyphornctl reload all).
  • SIGUSR1 — Triggers hot reload of detection rules (equivalent to cyphornctl reload rules).
  • SIGUSR2 — Triggers hot reload of File Intelligence dataset (equivalent to cyphornctl reload intelligence).
# Signal-based reload example
sudo kill -HUP $(pidof cyphorn-engine)
sudo kill -USR1 $(pidof cyphorn-engine)
sudo kill -USR2 $(pidof cyphorn-engine)

8.1 Update Engine & Provider Architecture

CyphornIPS incorporates an enterprise update subsystem designed for safe, verifiable, and zero-downtime hot updates of detection rules and threat intelligence. The core update engine is decoupled from hosting infrastructure through the CyphornUpdateProvider interface.

ProviderAdapter TypeEndpoint ResolutionTypical Deployment Scenario
GitHub Provider CYPHORN_PROVIDER_GITHUB https://raw.githubusercontent.com/{repo}/{branch}/channels/{channel}/manifest.json Official community threat feeds, GitHub enterprise private repositories.
Generic HTTP Provider CYPHORN_PROVIDER_GENERIC_HTTP Direct URL passed via --manifest-url <url> Private corporate mirrors, Cloudflare R2, AWS S3, internal air-gapped web servers.
Why Provider Abstraction Matters

The core update engine only knows how to process manifests, verify SHA-256 digests, sandbox-validate syntax, and hot-reload. It does not depend on GitHub-specific API behavior. This design allows seamless migration from GitHub to private S3 buckets, Cloudflare R2, or internal CDN mirrors simply by supplying --manifest-url without touching the engine code.

8.2 Update Channels (stable)

CyphornIPS officially distributes detection rules and threat intelligence via the stable channel:

  • stable (Default): Rigorously verified, regression-tested rules and confirmed threat indicators for production gateways.

The --channel parameter defaults to stable. Additional channels (such as experimental/beta feeds) may be added in future releases.

bash — Channel Selection Examples

8.3 End-to-End Update Lifecycle & Automated Rollback

Updates follow a strict 13-stage atomic pipeline ensuring that corrupted or invalid updates can never impair production traffic:

StageOperationSafety Gate / Failure Handling
1. Provider ResolutionResolve manifest endpoint for GitHub or Generic HTTP.Fails safely with descriptive network/DNS error if unreachable.
2. Manifest DownloadRetrieve and parse manifest.json schema.Rejects malformed JSON; zero disk modifications.
3. Version ComparisonCompare remote version against /var/lib/cyphornips/version.json.Exits cleanly with "Up to date" unless --force is specified.
4. Artifact DownloadDownload rule archive and intelligence JSON to /var/lib/cyphornips/updates/staging/.Network failure aborts update; active rules untouched.
5. SHA-256 VerificationCompute OpenSSL SHA-256 hash of staged payload.Integrity Gate: Hash mismatch aborts update immediately.
6. StagingUnpack rules into isolated staging directories.Disk full or unpack errors cleanly abort before install.
7. Native Pre-ValidationConstruct sandbox combining Candidate Managed + Active Local rules. Parse with native engine.Validation Gate: Any syntax error aborts update. Zero production files modified.
8. Managed/Local ReconciliationIdentify managed rules vs. local user rules using canonical fingerprints.Preserves 100% of local rules in /etc/cyphornips/rules/local/.
9. Atomic InstallationSnapshot current managed/ to backup/. Atomically install new managed/rules.rules.Only managed/ and ownership.json are modified.
10. Zero-Downtime Hot ReloadIssue reload rules or reload all over Unix control socket.Running engine compiles new store in memory and swaps pointers.
11. Health VerificationVerify engine confirms reload success and reports advanced generation.If engine rejects reload, proceed immediately to Step 12 (Rollback).
12. Automated RollbackRestore managed/ and ownership.json from backup snapshot; trigger engine reload.Restores previous working state; local user rules remain untouched.
13. State PersistenceCommit new version and SHA-256 to /var/lib/cyphornips/version.json.Telemetry and version state finalized.
Validation Failure vs. Reload Failure

Validation Failure: Occurs in Step 7 before installation. The candidate update is rejected in staging. Zero production files on disk are touched.
Reload Failure: Occurs if the live engine rejects the candidate during runtime reload. The update system immediately executes Automated Rollback, restoring the previous working managed ruleset and resynchronizing the engine. Local user rules in /etc/cyphornips/rules/local/ are NEVER touched or rolled back.

Clean Shutdown

To safely shut down the interactive console and detach eBPF filters, press q or Q in the console UI, or send Ctrl+C (SIGINT).

9.2 Canonical Rule Fingerprinting

In traditional IDS engines, rule identity is tracked solely by the numerical Signature ID (sid:). In an enterprise environment, this leads to fatal rule collisions: if a local administrator creates a custom rule with sid:1000003 to drop specific traffic, an upstream update that also introduces sid:1000003 would either delete or overwrite the user's rule.

To eliminate this vulnerability, CyphornIPS derives a deterministic 64-character SHA-256 Canonical Fingerprint from the parsed representation of every rule:

Canonical Fingerprint Generation Pipeline
Raw Rule Text
    ↓
Parser (Syntactic Extraction)
    ↓
Canonical Key-Value Representation (act:2|proto:6|dir:0|src:192.168.1.0/24:any|dst:any:80|sid:1001|rev:1|msg:BLOCK HTTP|)
    ↓
OpenSSL EVP_sha256() Cryptographic Digest
    ↓
64-Character Canonical Hex Fingerprint (4a6c7b27a386ed575c595cbb067158f6daaa05ce70fc941d2e4af9d42848d199)
SID Collision Resolution Example

Consider an upstream managed rule and a local custom rule that share sid:1001:

  • Managed Rule: alert tcp any any -> any 80 (msg:"UPSTREAM ALERT"; sid:1001; rev:1;) → Fingerprint: 4060b09b15e356566b43291f22589812b74169ae...
  • Local Rule: drop tcp any any -> any 80 (msg:"LOCAL DROP"; sid:1001; rev:1;) → Fingerprint: 4a6c7b27a386ed575c595cbb067158f6daaa05ce...

Because their canonical fingerprints differ, CyphornIPS treats them as two completely distinct rules in /var/lib/cyphornips/rules/ownership.json. An update to the managed rule will never overwrite the local rule.

9.3 Flat-to-Hierarchical Migration (cyphornctl update migrate)

If upgrading from an earlier flat rule directory (/etc/cyphornips/rules/*.rules), run:

cyphornctl update migrate

The migration tool creates managed/ and local/, moves rules.rules to managed/, moves all other local rules to local/, generates canonical fingerprints, pre-validates in a sandbox, and verifies live engine reload before committing disk changes with zero rule loss.

10 IP & CIDR Rules

CyphornIPS provides high-performance Layer 3 network address filtering supporting individual host addresses, CIDR subnet ranges, multi-address lists, and exclusion negation.

Address-Family Evaluation Semantics

  • IPv4 Selectors: Positive IPv4 selectors evaluate and match against IPv4 packets only.
  • IPv6 Selectors: Positive IPv6 selectors evaluate and match against IPv6 packets only.
  • Address Family Isolation: IPv4-only selectors never match IPv6 traffic, and IPv6-only selectors never match IPv4 traffic.
  • Mixed Selectors: Lists containing both IPv4 and IPv6 subnets (e.g. [192.0.2.0/24, 2001:db8::/32]) match packets corresponding to each respective address family.
  • Negation: Negated address selectors (e.g. !192.0.2.10) exclude specified addresses from matching.

12.1 NOCASE — Case-Insensitive Pattern Matching

Syntax: content:"<pattern>"; nocase;

What it does: The nocase modifier instructs the CyphornIPS pattern matching engine to perform case-insensitive byte comparisons using byte_equal_nocase(). Uppercase ASCII letters (A-Z) match lowercase ASCII letters (a-z) and vice versa.

Practical Security Use Case: Adversaries frequently alter character casing (e.g., Cmd.Exe, cMd.eXe, UnIoN SeLeCt) to evade naive signature detection engines. Using nocase guarantees detection regardless of letter casing used by attackers or varied client implementations.

Example Rule:

alert tcp any any -> any any (msg:"cmd exe Alert"; content:"cmd.exe"; nocase; sid:2501; rev:1;)

Concrete Test Matrix:

  • cmd.exe → MATCH (exact match)
  • CMD.EXE → MATCH (uppercase match)
  • Cmd.Exe → MATCH (mixed-case match)
  • cmdXexe → NO MATCH (mismatch character)
  • hello → NO MATCH (unrelated payload)

Positive Test Command (Client via Scapy):

bash (Client)
sudo python3 -c 'from scapy.all import IP,TCP,Raw,send; send(IP(dst="192.168.10.1")/TCP(sport=50001,dport=80,flags="PA")/Raw(load=b"GET /run?bin=CMD.EXE HTTP/1.1\r\n"),verbose=False)'

Expected Alert:

[ALERT] SID=2501 ACTION=ALERT PROTO=TCP SRC=...:50001 DST=...:80 MSG="cmd exe Alert"

Negative Test Command (Client via Scapy):

bash (Client)
# Mismatched payload must NOT trigger SID 2501
sudo python3 -c 'from scapy.all import IP,TCP,Raw,send; send(IP(dst="192.168.10.1")/TCP(sport=50002,dport=80,flags="PA")/Raw(load=b"GET /run?bin=cmdXexe HTTP/1.1\r\n"),verbose=False)'

Limitations & Common Mistakes:

  • nocase applies strictly to ASCII alphabetical bytes (0x41-0x5A and 0x61-0x7A). Non-alphabetical and binary bytes remain unchanged.
  • Do not apply nocase on binary patterns where byte values are fixed (e.g. |00 ff|); it has no effect on non-letters.

12.2 OFFSET — Absolute Starting Position

Syntax: content:"<pattern>"; offset:<N>;

What it does: Sets the starting search position to an absolute 0-indexed byte offset N from the start of the inspected buffer. The engine will not search for the pattern anywhere before byte N.

Important Clarification: offset refers strictly to the byte index within the application payload or sticky buffer. It is completely independent of TCP sequence numbers (seq:).

Practical Security Use Case: Validating protocol headers and fixed-format structures where a token or magic byte is expected at a known position (e.g. verifying an HTTP response status line starting at byte 0, or an ELF file magic header).

Example Rule:

alert tcp any any -> any any (msg:"HTTP marker at offset 0"; content:"HTTP/1.1"; offset:0; sid:2502; rev:1;)

Concrete Test Matrix:

  • HTTP/1.1 200 OK\r\n (starts at index 0) → MATCH
  • HTTP/1.1 200 OK\r\n (starts at index 3) → NO MATCH (if paired with depth)

Positive Test Command (Client via Scapy):

bash (Client)
sudo python3 -c 'from scapy.all import IP,TCP,Raw,send; send(IP(dst="192.168.10.1")/TCP(sport=50003,dport=80,flags="PA")/Raw(load=b"HTTP/1.1 200 OK\r\nServer: Test\r\n\r\n"),verbose=False)'

Expected Alert:

[ALERT] SID=2502 ACTION=ALERT PROTO=TCP SRC=...:50003 DST=...:80 MSG="HTTP marker at offset 0"

Limitations & Common Mistakes:

  • offset cannot be used on relative content patterns that use distance.
  • offset is mutually exclusive with startswith.

12.3 DEPTH — Search Window Restriction

Syntax: content:"<pattern>"; depth:<N>; or content:"<pattern>"; offset:<O>; depth:<D>;

What it does: Restricts the search range to at most N bytes from the buffer start (or within D bytes starting from offset O, terminating search at byte position O + D).

Practical Security Use Case: Restricting signature inspection to file headers or command verbs located in the initial portion of a stream. This prevents false positives from user data deeper in the payload and saves inspection CPU cycles.

Example Rule:

alert tcp any any -> any any (msg:"PE header"; content:"MZ"; offset:0; depth:2; sid:2503; rev:1;)

  • \x00\x00MZ\x90\x00\x03\x00 (pattern at index 2, outside depth 2) → NO MATCH

12.4 DISTANCE — Relative Pattern Starting Offset

Syntax: content:"p1"; content:"p2"; distance:<N>;

What it does: Specifies that the search for pattern p2 must start N bytes after the end of the match for preceding pattern p1 (i.e. search_start = match_end(p1) + N).

Practical Security Use Case: Detecting multi-token command formats and protocol sequences (e.g. FTP/SMTP USER admin where exactly 1 space separates the command and username, or specific query parameters in URLs).

Example Rule:

alert tcp any any -> any any (msg:"USER followed by admin"; content:"USER"; content:"admin"; distance:1; sid:2504; rev:1;)

Byte Position Analysis:

  • Payload: USER admin\r\n
  • USER matches at bytes [0..3] (length 4, match_end = 4).
  • distance:1 sets search start for admin at 4 + 1 = 5 (byte 5 is a).
  • admin matches at bytes [5..9] → MATCH.

bash (Client)

12.5 WITHIN — Relative Search Window Restriction

Syntax: content:"p1"; content:"p2"; distance:<D>; within:<W>;

What it does: Restricts the search for pattern p2 to conclude within W bytes relative to the end of pattern p1 (or relative to the distance start point).

Difference between DISTANCE and WITHIN:

  • distance defines where the search begins relative to the previous match.
  • within defines the maximum span of the search window relative to the previous match.

Example Rule:

alert tcp any any -> any any (msg:"PASS followed by secret"; content:"PASS"; content:"secret"; distance:1; within:10; sid:2505; rev:1;)

Byte Position Breakdown:

  • Payload: PASS secret\r\n
  • PASS matches at bytes [0..3] (match_end = 4).
  • distance:1 sets search origin to byte 5.
  • within:10 bounds the search window between bytes 5 and 15.
  • secret ends at byte 11 (within bound 15) → MATCH.
  • If secret appeared 30 bytes later (past byte 15) → NO MATCH.

12.9 FAST_PATTERN — Multi-Pattern Prefilter Acceleration

Syntax: content:"<pattern>"; fast_pattern;

What it does: Designates a specific content pattern as the primary prefilter pattern for multi-pattern hardware and software acceleration. During scanning, CyphornIPS tests the fast pattern first in a single prefilter pass; if the fast pattern is absent, the entire rule is skipped immediately without evaluating subsequent costly modifiers.

Automatic Fast Pattern Selection in CyphornIPS:

  • If fast_pattern; is explicitly specified, CyphornIPS uses that pattern directly.
  • If omitted, CyphornIPS automatically calculates a Pattern Strength Score based on pattern length, byte uniqueness, and character distribution, picking the least common pattern as the prefilter.

Important Note: fast_pattern does NOT alter detection semantics or matching logic; it is purely a performance optimization to maximize packet throughput.

Example Rule:

alert tcp any any -> any any (msg:"Sensitive admin API"; content:"GET"; content:"/sensitive_admin_api"; fast_pattern; sid:2509; rev:1;)

When to use: When a rule contains a short generic token (such as GET) and a long, unique token (such as /sensitive_admin_api). Explicitly designating the long token as fast_pattern prevents unnecessary prefilter matches on every HTTP GET request.

13.1 File Inspection, Extraction & Hashing Subsystem

CyphornIPS incorporates a high-performance in-memory stream reassembly and file extraction pipeline designed to reconstruct, hash, classify, and inspect transmitted files across application layer protocols.

Extraction Pipeline & Protocol Adapters

  • HTTP Request Bodies (to_server): Reassembles client upload streams (HTTP POST, PUT) with Content-Length or Transfer-Encoding: chunked. Infers filenames from Content-Disposition: attachment; filename="..." headers or from the request URI path.
  • HTTP Response Bodies (to_client): Reassembles server download streams. Infers filenames from Content-Disposition headers or from the requested URI path.
  • FTP Data Transfers (ftp-data): Stateful inspection dynamically tracks FTP control channel commands (PORT, PASV, EPRT, EPSV) and extracts data stream payloads associated with STOR (upload) and RETR (download) commands. The active command is exposed via the ftpdata_command rule keyword.
  • Unsupported File Extraction Protocols: While protocol identifiers for smtp, smb, and nfs are recognized by the rule parser, the current runtime engine does not implement payload file extraction adapters for SMTP, SMB, NFS, ICMP, or generic raw TCP. Rules targeting these protocols for file extraction parse successfully but will not trigger file inspection events at runtime.

Reassembly Limits & Memory Safety

To prevent resource exhaustion attacks and memory unbounded growth during large file transfers, CyphornIPS enforces strict kernel and user-space bounds:

Parameter ConstantDefault LimitEnforcement Behavior
CYPHORN_FILE_MAX_SIZE16 MiB (16,777,216 bytes)Maximum reassembled size per single file object. Streams exceeding 16 MiB are marked truncated (complete = false) and rejected from full inspection and disk storage.
CYPHORN_FILE_DEFAULT_MAX_MEMORY32 MiB (33,554,432 bytes)Global memory ceiling allocated across all concurrent in-flight stream reassemblies.
CYPHORN_FILE_DEFAULT_MAX_CHUNKS4,096 chunksMaximum discrete TCP chunk allocations per reassembly session.

Cryptographic Hashing Subsystem

Upon stream completion and verification (complete == true), CyphornIPS computes four standard cryptographic hash digests over the complete reassembled byte buffer in a single pass using OpenSSL EVP:

  1. MD5: 32 lowercase hexadecimal characters (128-bit digest).
  2. SHA-1: 40 lowercase hexadecimal characters (160-bit digest).
  3. SHA-256: 64 lowercase hexadecimal characters (256-bit digest).
  4. SHA3-384: 96 lowercase hexadecimal characters (384-bit digest).

Magic Header & Metadata Classification

The reassembled buffer is evaluated by the internal classification engine detect_magic() to extract file properties:

  • PDF Documents: Header magic %PDF- sets magic description to PDF document and MIME to application/pdf.
  • JPEG Images: Magic bytes \xFF\xD8\xFF set magic description to JPEG image data (with JFIF standard when present) and MIME to image/jpeg.
  • PNG Images: Magic bytes \x89PNG\r\n\x1a\n decode IHDR chunk dimensions (e.g. PNG image data, 1 x 1,) and MIME to image/png.
  • GIF Images: Magic bytes GIF87a / GIF89a decode screen dimensions and MIME to image/gif.
  • Windows / DOS Executables: DOS stub MZ header followed by valid PE signature offset sets magic description to executable for MS Windows and MIME to application/x-dosexec.
  • Short Files (< 4 bytes): Files smaller than 4 bytes are assigned very short file (no magic) and MIME application/octet-stream.
  • Extension Normalization: File extensions are derived from the inferred filename and normalized to lowercase (e.g. .JPG → jpg).

Filestore Subsystem & Artifact Archival

  • Storage Directory: /var/log/cyphornips/files (configurable via environment variable CYPHORNIPS_FILE_STORE_DIR).
  • Binary Payload File: Stored under its SHA-256 hash digest (e.g. /var/log/cyphornips/files/c028d7aa15e851b0eefb31638a1856498a237faf1829050832d3b9b19f9ab75f) with secure permissions (0640).

  • Syntax: filemd5:<filename>;, filesha1:<filename>;, filesha256:<filename>;.
  • List File Resolution: Resolved relative to rules_dir (e.g. /etc/cyphornips/rules/fileextraction-chksum.list). Path traversal sequences (..) are strictly rejected.
  • List File Format: Flat text file with one hexadecimal hash per line. Blank lines and comments starting with # or ; are ignored. Leading and trailing whitespace and CRLF line endings are stripped. Hex characters are normalized to lowercase.
  • Strict Validation: Each line must contain exactly the required number of hex characters (32 for MD5, 40 for SHA-1, 64 for SHA-256). Any invalid character or incorrect length causes immediate failure during rule loading. Missing list files safely prevent rule activation without crashing.
  • Lookup Performance: Hash lists are loaded into contiguous memory, sorted via qsort(), and queried at runtime via bsearch() in $O(\log N)$ time.
  • Inline Hashes: Note that inline hash strings (e.g. filemd5:"d41d8cd98f00b204e9800998ecf8427e") are not supported in rule definitions; checksum rules require a reference to a list file.

File Payload Pattern Matching (file.data)

The file.data (or file_data) sticky buffer exposes the full reassembled file byte buffer to standard CyphornIPS content matching:

alert http any any -> any any (msg:"Embedded Malicious Script in Upload"; file.data; content:"<script>eval("; nocase; sid:3403; rev:1;)

Supported modifiers on file.data include: nocase, depth, offset, distance, within, and byte_test. Note that pcre, byte_jump, and filesize keywords are not supported.

13.2 File Intelligence Threat Engine (Normalized JSON Dataset)

In addition to rule-based signature matching (files.rules), CyphornIPS includes a dedicated File Intelligence Subsystem. It is designed for high-scale ingestion of IOC hash datasets from external threat intelligence feeds without the overhead of generating thousands of separate rule ASTs.

Core Detection Specifications

  • Supported Hashes: The engine validates exact matches against four supported hash fields:
    1. sha256_hash (64 hex characters)
    2. sha3_384_hash (96 hex characters)
    3. sha1_hash (40 hex characters)
    4. md5_hash (32 hex characters)
  • Evaluation Priority: For every completed extracted file, hashes are evaluated in order: SHA-256 → SHA3-384 → SHA-1 → MD5. A match on ANY ONE of the populated hash fields triggers detection.
  • Supported Metadata Fields:
    • file_name — Nominal or known threat filename string.
    • file_type_mime — MIME type classification string (e.g. application/x-dosexec, image/jpeg).
    • tags — Array of threat classification tags (e.g. ["malware", "ransomware", "c2"]).
  • Excluded / Unsupported Features: File Intelligence is strictly exact-hash matching. It does not support fuzzy matching, SSDEEP, TLSH, imphash, Telfhash, Gimphash, dhash, TRiD, reputation scoring, or machine learning classification.
  • Alert Generation & Event Details: Detections emit a security alert under dedicated Signature ID SID 9100000 with full metadata rendered in the UI Event Details:

Administrator Operations Guide

Follow these operational workflows for maintaining and updating threat intelligence in production:

1. Adding a Custom Threat Fingerprint:

  1. Calculate the cryptographic hashes of the target file: 
    sha256sum suspicious.exe
openssl dgst -sha3-384 suspicious.exe
sha1sum suspicious.exe
md5sum suspicious.exe
  2. Add a new JSON record entry into /etc/cyphornips/rules/cyphorn-file-intelligence.json. At least one valid hash field must be provided.
  3. Validate the JSON syntax prior to deployment: 
    python3 -m json.tool /etc/cyphornips/rules/cyphorn-file-intelligence.json > /dev/null && echo "JSON syntax OK"

2. Updating Threat Intelligence Without Engine Restart:

  1. Trigger an in-memory hot reload of the File Intelligence table: 
    cyphornctl reload intelligence
  2. Verify that the new dataset records are active: 
    cyphornctl status

    Check that Intel Records reflects the expected record count and Last Intel Reload is updated.

3. Failed Dataset Update Handling & Rollback:

If an updated JSON dataset file contains invalid JSON syntax or unparseable structures, CyphornIPS automatically rejects the update, records an error in /var/log/cyphornips/cyphornips.log, and preserves the existing active dataset in memory. Live traffic inspection continues without interruption.

4. External Intelligence Synchronization Architecture:

For automated multi-feed environments, use an external sync worker to fetch threat feeds, normalize them to the standard Cyphorn JSON schema, and signal the engine:

[ External Threat Feeds / TAXII / MISP ]
                   ↓ (Periodic Sync Script)
  [ Normalized JSON File: /etc/cyphornips/rules/cyphorn-file-intelligence.json ]
                   ↓ (cyphornctl reload intelligence OR kill -USR2)
  [ Running CyphornIPS Process — Zero-Downtime Atomic Pointer Swap ]

13.6 Practical Rule Reference (/etc/cyphornips/rules/files.rules)

Runtime model

HTTP and FTP-data are the implemented adapters: complete request and response bodies and FTP data streams are inspected; filenames come from upload metadata, FTP commands, or URI paths; extensions are lowercased; MD5/SHA-1/SHA-256/SHA3-384 and bounded magic descriptions are generated.

Actions: all rules below use alert; none drops traffic. noalert still permits matching and filestore, but suppresses the user-visible alert. Storage requires a complete, non-empty file and is limited to 16 MiB.

Filestore: default path is /var/log/cyphornips/files, overridden by $CYPHORNIPS_FILE_STORE_DIR. Files use generated SHA-256 names and JSON sidecars; the original filename is not used as a path.

SMTP, SMB, and NFS: their rules parse, but the current runtime has no file-extraction adapter for these protocols.

Reusable HTTP test: send a complete body with a known name, then check the rule result and (when applicable) the generated file and JSON sidecar:

curl -H 'Content-Type: application/octet-stream' \
     --data-binary @sample.pdf http://sensor/upload/photo.jpg

Choosing the right file rule

  • Use fileext for what the sender claims; pair it with filemagic for what the bytes actually are.
  • Use filemagic for type, dimensions, and negative checks. It is a substring match unless a binary terminator such as |00| is included.
  • Use filemd5, filesha1, and filesha256 to match IOC blacklist feeds. Checksum lists reside under /etc/cyphornips/rules/ (one hash per line, comments # / ; and whitespace ignored, strictly validated).
  • Use file.data to search original bytes with content; use filestore when another tool needs the complete artifact.
  • Use noalert for silent collection. It does not disable matching or storage. The current files.rules set contains no file-drop rule.
  • Do not treat SIDs 3364, 3369, and 3370 as active attachment capture until the SMTP, SMB, and NFS adapters are implemented.

16 Action Precedence & Multi-Rule Conflict Resolution

In high-throughput enterprise environments, a single transit packet frequently satisfies the criteria of multiple detection rules simultaneously. To guarantee deterministic, safe, and predictable packet verdicts, CyphornIPS executes a two-stage evaluation engine governed by the strict Action Precedence Hierarchy implemented in src/action.c:

Action Precedence Hierarchy (src/action.c)
PASS (Priority 3)  >  DROP / REJECT (Priority 2)  >  ALERT (Priority 1)
ActionPriorityEngine VerdicteBPF Filter EffectAlert Emitted?Operational Role
pass 3 (Highest) CYPHORN_VERDICT_ALLOW Forwarded across bridge immediately No Explicit administrative whitelisting. Overrides all matching DROP, REJECT, and ALERT rules.
drop 2 (High) CYPHORN_VERDICT_DROP Dropped immediately via kernel eBPF map Yes Active threat prevention and inline payload blocking. Overrides matching ALERT rules.
reject / reject_src / reject_dst / reject_both 2 (High) CYPHORN_VERDICT_DROP Dropped with TCP RST / ICMP Unreachable injection Yes Active blocking with immediate client/server connection termination.
alert 1 (Normal) CYPHORN_VERDICT_ALLOW Forwarded across bridge normally Yes Passive threat observability, audit logging, and signature tuning.

Multi-Rule Conflict Resolution Scenarios

Scenario 1: PASS vs. DROP Conflict (Whitelist Override)

Rule A (DROP): drop tcp any any -> any 443 (msg:"Block External SSL"; sid:1000003;)
Rule B (PASS): pass tcp 192.168.1.50 any -> any 443 (msg:"Allow Management Host"; sid:9999001;)
Outcome: When 192.168.1.50 initiates an HTTPS connection, both rules match. Because PASS (Priority 3) > DROP (Priority 2), Rule B wins. The packet is forwarded across the bridge. Rule B telemetry records an [EFFECTIVE] hit, while Rule A is marked as [OVERRIDDEN] (OVRD). No alert is written to disk.

Scenario 2: DROP vs. ALERT Conflict (Enforcement Priority)

Rule A (ALERT): alert tcp any any -> any 80 (msg:"HTTP Inbound Observed"; sid:1000010;)
Rule B (DROP): drop tcp any any -> any 80 (msg:"SQL Injection in URI"; http.uri; content:"UNION SELECT"; sid:1000020;)
Outcome: An attacker transmits a SQL injection payload over port 80. Both rules match. Because DROP (Priority 2) > ALERT (Priority 1), Rule B wins. The packet is dropped immediately inline. Rule B records a [DROPPED] and [EFFECTIVE] hit and logs an alert. Rule A is marked as [OVERRIDDEN] (OVRD).

CRITICAL: Rule Ownership vs. Action Precedence

Rule Ownership (MANAGED vs. LOCAL) has NO effect on action precedence.
- LOCAL rules do not automatically override MANAGED rules.
- MANAGED rules do not automatically override LOCAL rules.
Ownership answers: "Who controls the file on disk?" (Update Engine vs Administrator).
Action Precedence answers: "Which action wins the packet verdict?" (PASS > DROP > ALERT).
If you want a local rule to override an upstream managed DROP rule, declare your local rule with the pass action!

20.1 Operational Safety: What an Administrator Should NEVER Do

Golden Rules of CyphornIPS Administration
  • NEVER manually edit files inside /etc/cyphornips/rules/managed/: The update subsystem manages this directory exclusively. Manual changes will be overwritten on the next update. Put all custom rules in /etc/cyphornips/rules/local/.
  • NEVER rely on SID alone to determine rule identity: Upstream rules and local rules can share SIDs. CyphornIPS differentiates rules by their 64-character Canonical Fingerprint.
  • NEVER delete /etc/cyphornips/rules/local/ when troubleshooting: Managed rule updates and automated rollbacks only touch managed/. Deleting local/ destroys your custom whitelists and local signatures permanently.
  • NEVER assume MATCHED means traffic was blocked: A rule with 1,000 matches may have been overridden by a pass rule. Check the [EFFECTIVE] and [DROPPED] counters.
  • NEVER assume OVRD means a rule is broken: OVRD indicates that a higher-priority action (such as an administrative pass whitelist) successfully protected traffic from a lower-priority drop rule.

21 Security Considerations

  • Administrative Privileges: Raw packet capture and inline network filtering require elevated system privileges. Restrict write access to configuration files and rule directories to authorized administrators.
  • Configuration File Protection: Ensure configuration files (cyphornips.conf and domain_policy.conf) are owned by root with restrictive file permissions (e.g. chmod 600).
  • Log Integrity: Ensure log storage on /var/log/cyphornips/ has sufficient disk capacity and appropriate log retention settings.
  • Testing Before Enforcement: Test new rules with the alert action in non-blocking mode before changing them to drop to prevent accidental disruption of legitimate traffic.

22 Limitations & Known Constraints

  • File Extraction Protocols: File reassembly and extraction adapters are strictly implemented for HTTP (request and response streams) and FTP-data (active and passive transfers). Rules targeting smtp, smb, or nfs parse successfully but will not extract files or trigger file rules at runtime.
  • File Size Ceiling: Single file reassembly is bounded at 16 MiB (CYPHORN_FILE_MAX_SIZE). Streams exceeding 16 MiB are marked truncated and rejected from full inspection and disk archival.
  • Unsupported File Rule Keywords: The 0.1.0 engine does not support pcre, byte_jump, or filesize keywords.
  • File Intelligence Exact Matching: File Intelligence matching is strictly exact cryptographic hash matching across SHA-256, SHA3-384, SHA-1, and MD5. Fuzzy hashing (SSDEEP/TLSH), imphash, reputation scoring, and AI/ML classification are intentionally not supported.
  • Software Updates vs Rule Updates: Replacing the engine binary requires a process restart (systemctl restart cyphornips). Modifying signature rules or threat intelligence datasets does not require restart and is performed live via cyphornctl.
  • GeoIP Country Lookups: GeoIP country database lookup (geoip:) is Not available / Not enabled in CyphornIPS 0.1.0. Automatic database initialization is not enabled in this release; rules must not rely on geoip:.
  • Encrypted Payload Inspection: CyphornIPS inspects unencrypted TLS handshake metadata (SNI, certificates, versions). It does not perform active SSL/TLS proxying or payload decryption.
  • HTTP Protocols: Full inspection is supported for HTTP/1.0 and HTTP/1.1. HTTP/2 and HTTP/3 multiplexed binary stream inspection is currently planned.
  • Inline Network Topology: Inline blocking requires the host to be positioned directly in the network traffic path between the WAN and LAN segments.

Operational Case Study: Overly Broad Pattern Matching

Consider an administrator who creates the following inline blocking rule targeting administrative brute-force attempts: 

drop tcp any any -> any 80 (msg:"Block Web Admin Access"; http.uri; content:"admin"; sid:9900001; rev:1;)

The Problem: While syntactically valid, the pattern "admin" is overly broad. It will match and unconditionally drop legitimate client requests to URIs such as:

  • /assets/js/admin-tools.min.js (Legitimate JavaScript asset)
  • /portal/readmission/status (Legitimate user portal)
  • /documentation/administrator-guide.html (Legitimate public resource)

Best Practice: Always deploy new signatures initially with the alert action in non-blocking mode. Monitor match counts and inspect false-positive rates on Screen 4 (Rule Inspector) before elevating rules to drop or reject.

23 Frequently Asked Questions

Q: How does CyphornIPS differ from a traditional firewall?

A: A traditional firewall typically filters based on Layer 3/4 headers (IP and port). CyphornIPS is a stateful Intrusion Prevention System that inspects application protocol metadata (HTTP, TLS), matches payload content patterns, and enforces domain intelligence policies.

Q: How do I update rules or threat intelligence without dropping packets?

A: Use the cyphornctl reload rules or cyphornctl reload intelligence commands. The running engine compiles and validates the new datasets in isolated staging memory and atomically swaps pointers with zero downtime.

Q: Can I run CyphornIPS without specifying a domain policy file?

A: Yes. CyphornIPS automatically looks for /etc/cyphornips/domain_policy.conf (or domain_policy.conf in the working directory). If no file is found, it initializes with an empty domain table and continues normal rule inspection.

Q: Where should I place custom signature rules?

A: Place custom .rules files in /etc/cyphornips/rules/local/. Never edit /etc/cyphornips/rules/managed/rules.rules directly.
